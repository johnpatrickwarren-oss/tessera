### 1.3 Why filter-repo (not subtree split, not manual copy)

| Approach | Outcome | Trade-off |
|---|---|---|
| **`git filter-repo --subdirectory-filter`** (PICKED) | Rewrites history; new repo has full per-commit-touching-engine/ history with `engine/` removed from path; tree at HEAD byte-identical to Tessera HEAD `engine/` subtree | Requires `git-filter-repo` install (one-time); history-preserving (commit SHAs change but commit dates + messages + per-file blame chains survive); canonical for this exact use case per git-filter-repo documentation |
| `git subtree split --prefix=engine` | Similar to filter-repo but slower on large histories; built into core git | Less canonical; slower; produces same byte-identical tree but harder to verify completeness |
| Manual `cp -r engine /tmp/new-repo && git init` | Trivial; no history preservation | Loses provenance (blame chain back to R01 vendoring + Tessera-evolution deltas); violates directive operator-decision "History preservation: YES" |

Operator decided **filter-repo** per directive header. Decision is load-bearing for provenance.

### 1.4 Why git-dep (not npm publish)

| Approach | R94 cost | Trade-off |
|---|---|---|
| **git-dep `github:johnpatrickwarren-oss/deploysignal-engine#v0.1.0-pre`** (PICKED) | New repo + tag + 1-line package.json change | No npm registry coupling; works offline; consumable from any project with git access; tag immutable (semver-equivalent) |
| npm publish `@johnpatrickwarren-oss/deploysignal-engine@0.1.0-pre` | New repo + tag + `npm publish` invocation + 2FA confirmation | Faster install (npm CDN); registry-namespaced; but introduces registry-side state that's harder to revoke; out of scope for R94 (directive operator-locked decision: git-dep first cycle) |

### 1.5 Why drop tsconfig paths (not repoint to node_modules)

After R94 the `@johnpatrickwarren-oss/deploysignal-engine[/*]` package resolves via `node_modules/@johnpatrickwarren-oss/deploysignal-engine/` (pnpm's standard symlinked layout). TypeScript's default `moduleResolution: "node"` (already set at `tsconfig.json:6`) finds packages in `node_modules/` without any `paths` mapping required. Adding `paths` repointing to `node_modules/...` is redundant. Architect picks DROP.

Trade-off: if a future round needs path-aliased imports for IDE-specific resolution, that's an additive change at that point; not load-bearing at R94.
